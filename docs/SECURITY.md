# Security and privacy

Harness uses public AppKit, Carbon, ScreenCaptureKit, Security and OAuth APIs. It has no login item, privileged helper, event tap, continuous capture, audio capture or private recording hook. Mode 2 and legacy window flags do not prove third-party recording exclusion.

Starting the app indicates agreement to send each physical-shortcut screenshot and recent text context to OpenAI through the connected ChatGPT plan. The main window discloses this. Sign-in enables analysis without another checkbox; disconnect revokes transmission and cancels work. A screenshot still requires the physical registered capture key, verified capture scope and granted Screen Recording. Submission requires a valid account/model, applied masks when configured, and mandatory metadata audit. Failures never cause automatic image replay.

Images, processed JPEGs, request bodies and answer history stay as memory references. Dismissal, replacement, cancellation, disconnect and termination clear retained application content. There are no screenshot/clipboard files. This is not physical RAM erasure and cannot prevent OS swap, framework copies or provider retention. Requests use `store:false`, ephemeral sessions, no redirects/cookies/persistent cache and finite lifetimes.

Tokens/expiry persist together in Keychain service `org.harness.research.chatgpt`, account `accounts`. Nonsecret preferences and the host UUID use UserDefaults. No Codex/browser credentials are read. Tokens do not belong in source control, `.gitignore`, environment files, arguments, logs or support transcripts.

Custom system prompts are ordinary local preferences and are sent to OpenAI with inference requests. They are not encrypted credential storage; do not paste secrets into the prompt editor. They never enter audit/report files. Public OAuth endpoints, `dynamic_agent_client`, app identifiers and synthetic test values are protocol/configuration data, not embedded user credentials. Issued client IDs, host IDs and real tokens are created per installation and remain outside the repository.

Routine Keychain operations suppress both modern and legacy authorization UI and restore the previous process policy. Explicit account recovery alone permits a dialog, on a worker thread. Concurrent quiet operations fail promptly while that worker holds the policy lock. Cancellation does not dismiss a protected macOS dialog but prevents its late result being adopted. Self-signed updates may require authorization for a new executable hash; this is OS policy, not an app-owned lifetime grant. Public releases need stable Developer ID signing and notarization.

OAuth uses an IPv4 loopback listener, unique callback parameters, state/PKCE/nonce and validated RS256 issuer/audience/subject/expiry. Wrong-state or unrelated local requests do not consume the callback. Connection count, header bytes and listener lifetime are bounded. No tokens appear in callback logs. Account transactions and rotating refresh use private empty lock files; OS locks release on process death and are never stolen/unlinked. Generation guards stop stale credentials after cancellation/disconnect. Temporary network failures preserve credentials; confirmed unusable refresh tokens are cleared.

The popup is bounded literal native text. It has no active links, HTML execution, attachments or remote images. Screenshot text is treated as untrusted model input; the model has no tools or execution path. Resource limits are specified in [SPEC.md](SPEC.md).

Audit/detection/report files contain allowlisted metadata: app/process/window identities, geometry, timestamps, byte counts/hashes and failure classifications. They exclude screenshot content, prompts, responses, tokens, callback URLs and window titles. Files use private/no-follow creation, complete writes, bounded locks and finite EINTR retries. Audit failures stop sensitive actions. Ordinary JSONL is not authenticated/tamper-proof, and report replacement is not crash-atomic. Metadata can reveal usage patterns; review before sharing.

Runtime data is under `~/Library/Application Support/harness/`, macOS preferences and Keychain. Preserve it during upgrades. Development signing material uses the owned signing Keychain and precisely named login-Keychain secret; unrelated entries and system trust are untouched. The installer validates paths, expansion limits, CRC, bundle identity/signatures and update identity before an atomic swap.

Source releases contain reviewed tracked files only, with no Git history or runtime data. Binary releases remap compilation paths, strip debugging information before signing and run the same credential/path guard on the archives. Tests use generated credential-shaped values only. Scanner coverage is deliberately explicit; a scan is not a comprehensive secret-detection guarantee. Review newly added files and signing inputs before distributing them.
